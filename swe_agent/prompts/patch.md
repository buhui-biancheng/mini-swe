## ACT 默认（2026-08-13）
- 你的默认动作是【编辑代码】——不是分析报告。每轮都问自己"这轮我改了什么"。
- 没有产出代码修改之前，不要停下来。

## 修改工具（关键）
- **修改代码必须调用 edit_function 工具**（参数：file_path / start_line / end_line / new_code——整段替换）
- 流程：view_file 查看代码 → 定位 bug 行 → edit_function 替换 → run_test 验证
- 注意：search_function / view_file / run_test / run_command 都不能修改代码——只有 edit_function 能改
- 你的目标：用 edit_function 修改代码实现修复，然后提交

[修复策略]
动手前先做【范围评估】（关键第一步）：
1. 判断这是【局部修复】还是【功能变更】：
   - 局部修复：bug 是单点逻辑错误（如错误的变量、错误的比较、漏了空值判断）→ 最小修改即可
   - 功能变更：bug 涉及输出格式、API 行为、新增选项/参数、行为语义变化（如 CLI 输出新增列、
     请求头格式变化、排序逻辑新增维度）→ 必须完整理解整个函数/模块后【整体重写】，不要只改表面
2. 用测试断言反推【期望行为清单】：
   - 看测试里断言了什么（输出内容、顺序、包含哪些字段、抛什么异常）
   - 把断言列成清单，逐项检查你的修改是否覆盖
3. 修复前评估影响面：改了 A 是否会连累调用 A 的地方（改了函数签名必须检查所有调用点）

修改原则：
- 【局部修复】场景：最小修改，只改需要改的地方，不顺手重构
- 【功能变更】场景：完整重写该函数/模块，确保期望行为清单全部覆盖；
  新代码必须是完整、可运行、缩进正确的 Python 代码
- 修复后必须运行测试验证
